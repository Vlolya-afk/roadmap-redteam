# 4.2 — Архитектура приложений, сессии, аутентификация

> **M04 · Этап 0 · 4 ч · 🟢 · артефакт:** `labs/m04-web-crypto/l02-app-map/`

## Цель

Понять, из чего состоит веб-приложение и где граница между «кто ты» и «что тебе можно». Это ключ к IDOR, broken access control и OAuth-атакам.

## Результат

- Рисуете карту приложения: frontend → API → БД, с точками доверия.
- Отличаете аутентификацию от авторизации.
- Находите IDOR в учебном приложении и объясняете причину.

## Теория

- Типовая архитектура: браузер → reverse proxy/WAF → app → БД/кэш/очередь.
- Аутентификация = «кто ты», авторизация = «что можно». Ошибка в второй — причина #1 по OWASP.
- Сессия: сервер хранит состояние, клиент — идентификатор в cookie.
- JWT: подписанный токен с claims; сервер не хранит состояние, но не может «отозвать» токен без blacklist.
- OAuth/OIDC: resource owner, client, authorization server, resource server; `state`, `PKCE`, `redirect_uri`.
- Same-origin policy: JS не читает ответы другого origin; CORS ослабляет это явно.
- IDOR/BOLA: объект доступен по ID, а проверка прав отсутствует.

## Лаборатория

### 1. Карта приложения

Откройте DVWA (`http://127.0.0.1:8080`) и Juice Shop (`http://127.0.0.1:3000`). В DevTools → Network пройдите логин и один функциональный запрос. Заполните таблицу:

| Компонент | Пример | Доверие |
|---|---|---|
| Браузер | JS, cookie | Не доверять |
| Прокси | nginx | Проверять заголовки |
| API | `/api/basket/1` | Проверять пользователя |
| БД | SQL | Параметризовать |

### 2. Сессия

```bash
curl -i -c /tmp/c.txt -d 'username=admin&password=password&Login=Login' \
  http://127.0.0.1:8080/login.php
cat /tmp/c.txt
```

Ожидаемо: `PHPSESSID` в cookie; флаги `HttpOnly` могут отсутствовать — зафиксируйте это как находку.

### 3. IDOR в Juice Shop

1. Войдите как тестовый пользователь.
2. Откройте корзину, посмотрите запрос `GET /rest/basket/<id>`.
3. Измените `<id>` на чужой (например, на 1) в Repeater.
4. Ожидаемо: если сервер вернул чужую корзину — это BOLA/IDOR.

Сформулируйте: «сервер проверяет аутентификацию, но не проверяет, что `basketId` принадлежит текущему пользователю».

### 4. CORS

```bash
curl -s -D - -o /dev/null -H 'Origin: http://evil.lab' http://127.0.0.1:3000/ \
  | grep -i 'access-control'
```

Ожидаемо: либо нет CORS-заголовков, либо конкретный origin. `Access-Control-Allow-Origin: *` вместе с credentials — ошибка.

### 5. OAuth-чеклист

Для любого OAuth-приложения проверьте: `state` (CSRF), `redirect_uri` (open redirect → code theft), `PKCE` для public client, срок жизни токена, scopes.

## Атака и защита

- **Атака:** IDOR, session fixation, JWT `alg:none`/слабый ключ, OAuth redirect_uri bypass, CSRF.
- **Детект:** доступ к объектам других пользователей, аномальные `redirect_uri`, токены с неверной подписью.
- **Фикс:** проверка владельца на каждом объекте, `HttpOnly/Secure/SameSite`, короткие токены + rotation, строгий allowlist redirect_uri, PKCE.
